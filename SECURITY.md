# Security

Jarvis is a local development tool. Don't expose its HTTP server to a public network or put it behind a public tunnel.

## Reporting a vulnerability

Use the repository's **Security, then Report a vulnerability** option when it's available. Keep credentials, private images, exploit payloads with personal data, and sensitive logs out of public issues. If private reporting isn't available, open an issue asking for a private channel without the vulnerability details.

## Security boundaries

- The server binds to loopback and checks Host, Origin, fetch metadata and a per-process session token before any state-changing operation.
- The Windows executable also requires a random per-launch key for every API route except public readiness. The launcher passes it in the child environment, the server removes it before spawning the CLI, and the browser gets it in a URL fragment that is removed immediately. The key lives in origin-isolated session storage and travels only in an API request header. No auth cookie, because cookies cross loopback ports. Unauthenticated local clients can't obtain a session bearer or use an existing one without this desktop key. Preview URLs are separate random 160-bit capabilities issued only after an authenticated request. Don't share them with untrusted processes.
- Screen capture uses the browser permission picker, requests no audio, and stays local by default. Live build needs separate provider-specific consent before it sends changed snapshots automatically. It serializes builds, enforces a minimum interval and a ten-request cap per start, and stops on pause, capture loss, errors or reload. The exact last sent frame stays reviewable. These client controls sit on top of the server-side concurrency and allowance limits. Generated previews can't request display capture.
- Camera preview stays in the browser. Building shares the selected image, direction and selected prototype source through the chosen subscription-authenticated Codex or Claude Code CLI, after consent.
- Jarvis doesn't load environment files or read subscription credentials. The CLI owns auth. API-key logins and provider fallback are rejected.
- Each model request uses an ephemeral working directory with command tools and integrations disabled. Codex runs in a read-only sandbox. Claude Code runs in safe mode with no executable tools, a strict empty MCP configuration, and only its internal StructuredOutput tool. Fable needs a paid first-party Claude subscription. Usage credits may be spent after the in-app warning and sharing consent.
- Incremental drafts accept HTML only from an active structured-output block. Reasoning, credentials and raw CLI output are never forwarded. Draft previews have scripts disabled and belong to one active build. Their capability URLs are revoked on completion, cancellation or failure. Drafts never persist in browser history.
- Generated HTML runs in an opaque-origin iframe sandbox with network requests, nested frames and form destinations blocked by content security policy. It gets no camera or microphone permission.
- Preview storage, input sizes, request duration, concurrency and local inference allowance are bounded. Invalid input doesn't spend inference allowance. A user may explicitly renew the local allowance. That doesn't change provider limits.
- Install and sign-in routes need the same local session and explicit consent as every other state-changing action. Codex installation uses a fixed official npm package and registry with install scripts disabled. The Windows Claude Code installer downloads a pinned official native archive, checks SHA-512 integrity and the Anthropic publisher signature, and installs per user. No Anthropic binaries are redistributed inside Jarvis. Sign-in delegates to the official CLI. Credentials and login output never reach the page.
- Codex discovery accepts the official npm package layout and metadata, not arbitrary executable names. Claude Code discovery also accepts official native locations and checks Anthropic signatures on Windows. This is installation validation. It doesn't protect against a local user editing installed package files.
- A lightweight local-session route allows preview and source recovery independent of subscription status. It uses the same Host, Origin and fetch-metadata boundary as every other route.
- The desktop companion hosts its local page in a separate persistent WebView2 profile. Its bounded conversation stays in that profile and isn't a bridge into the user's regular browser history or saved revisions. It has no ambient screen or microphone capture. An explicit current-window screenshot shows the exact frame requested, and local dictation and spoken replies are opt-in local features.

None of this makes generated code trustworthy. A generated page can still mislead a user or eat browser resources. Read downloaded HTML before running it outside the restricted preview. Local processes under the same OS account are outside the desktop server's authentication boundary. The developer source launch has no desktop bootstrap and trusts every native process on the machine. Don't use that mode on a machine with untrusted OS users.

The Windows build pins the Node archive SHA-256 and the Codex npm package integrity, and validates upstream executable publishers before running the bundled CLI. The outer Jarvis launcher is currently unsigned. Installation uses an immutable build-specific per-user directory and rejects ZIP paths outside it. The launcher refuses an occupied port, validates its own server instance, and owns a Windows Job Object that stops descendants if the launcher exits. It doesn't start at Windows login and doesn't update itself.

Reference images, directions and source revisions persist in Jarvis's desktop WebView profile until **New project** clears them. A browser profile from a source install, or an older browser-based install, stays separate. Preview copies stay in bounded server memory until eviction or server exit. Source versions persist. Application state entered inside a generated preview resets when it's reopened.

## Computer mode (0.7)

A separate opt-in broker uses the same local host and origin, desktop bootstrap and session checks. A random owning-tab token, a ten-minute lease, one-minute single-use proposals and per-action approval gate every Windows operation. Stop invalidates proposals, aborts inference and terminates the owned native controller. Ctrl+Shift+F12 is registered before arming. If registration fails, acting stays off. A delivered action can't be recalled. Native identity, runtime ID, AutomationId, control type, name, visibility, enabled state and password status are checked against a fresh target before anything happens.

The model still has no executable tools. It returns a structured proposal, and only the local broker executes approved UIA operations. Fixed launch targets are Notepad, Calculator and Paint, resolved from the Windows system directory or fixed registered Windows app IDs. No generic executable path, shell action, coordinate fallback or elevated helper exists. Explorer, protected window names and processes, password controls, address and terminal controls and command-like text are excluded. These filters are defense in depth, not a guarantee that a UI click can't run code or send data. The human has to review consequential actions in the target app. Malicious apps and other same-account processes are outside this boundary.

Planning reads a fresh bounded accessibility tree from the selected window, including non-password editable values. The sharing notice covers fresh text explicitly, since it can differ from an earlier local inspection. The result includes the exact sent snapshot for inspection. Don't select apps holding private information you don't intend to share. No Computer-mode screenshots or audio are collected. Jarvis doesn't persist runtime action history. Model providers may retain requests under their own terms.
